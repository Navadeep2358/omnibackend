# OmniCloud authentication backend

This backend provides account registration, email verification, password sign-in, password reset by email code, and persistent login sessions. Registration details and the verification code are held in backend memory until the code is accepted; no user row or verification code is written to MySQL before verification. After successful verification, the backend creates the verified user row and login session. Pending registrations expire after 10 minutes and are cleared if the backend restarts, so the person must register again after a restart. Password reset codes are stored in MySQL, expire after 10 minutes, and allow up to five attempts.

## Local development

Requirements: Node.js 22.5 or newer.

1. Start the MySQL server. On backend startup, OmniCloud creates the configured database and tables from `schema.sql`, then ensures the GCP, Azure, and AWS connection columns exist. The MySQL user in `.env` must be allowed to create the database and tables.
2. Copy `.env.example` to `.env`; enter your MySQL password, a long random `SESSION_SECRET`, a Google App Password for the Gmail sender, `OMNICLOUD_GCP_SERVICE_ACCOUNT_EMAIL`, and Azure settings if you configure Azure.
3. From this folder, run `npm install` once, then `npm run dev`.
4. In a second terminal, start the Vite app from `frontend/omnicloud` with `npm run dev`.

On startup, the backend initializes the database from `schema.sql` and then removes legacy unverified user rows and old email-verification codes created by earlier versions. `schema.sql` is the complete final schema for fresh installations. Initialization is idempotent and does not drop tables or disconnect existing AWS connections. For older installations, the backend adds the GCP, Azure, and AWS connection columns and adds the AWS sign-in status field if needed.

For live email, set `GMAIL_USER` and `GMAIL_APP_PASSWORD` in `.env`. The sender is that Gmail address. Google requires 2-Step Verification to create an App Password. Without those values, development codes are printed in the backend terminal.

The Vite development server forwards `/api` requests to port 3001. In production, build the frontend first and run this backend; it serves the built frontend from `frontend/omnicloud/dist`.

## Render production deployment

This repository is the Render API service. Create it from `render.yaml` (Blueprint) or connect this repository as a Docker web service. The Docker image installs Terraform and serves only the API; local Docker-based Git builds are deliberately disabled on Render because the hosted service has no access to your desktop Docker Engine. Build images in CI or use a backend host that can access Docker Engine for that workflow.

Before the first deploy, create a managed MySQL database and database/user with permission to create and alter tables. Set `MYSQL_HOST`, `MYSQL_PORT`, `MYSQL_USER`, `MYSQL_PASSWORD`, and `MYSQL_DATABASE` in Render. `MYSQL_CREATE_DATABASE=false` makes startup connect directly to the pre-created database; `MYSQL_SSL=true` enables certificate-verified TLS. Check the managed database provider's TLS instructions before enabling it. Keep the Render persistent disk mounted at `/var/data`; Terraform state and plugin cache are stored there. Start with one service instance because Terraform state is local to that disk and is not shared across instances.

Set `OMNICLOUD_PUBLIC_URL` to the Netlify site's final HTTPS origin and set the AWS SSO start, issuer, and region values. AWS IAM Identity Center uses device authorization, so no public callback URI registration is required. Render generates stable values for the session secret and SSO encryption key from the Blueprint; do not rotate the encryption key while saved AWS SSO sessions exist. Configure email and Azure service-principal values only if those features are enabled. GCP impersonation requires the configured OmniCloud service account to have `roles/iam.serviceAccountTokenCreator` on the customer service accounts and a supported workload-identity credential source in the hosting environment; a local developer ADC file is not available on Render.

The Blueprint's default `starter` plan and persistent disk are paid Render resources. Review current Render prices before creating them. A real deployment also needs the external database and production secrets; the repository files alone cannot provision those third-party account settings.

## Production AWS connection and Terraform provisioning

AWS access is a per-OmniCloud-user IAM Identity Center device-authorization flow. The user opens AWS's verification page and enters the one-time code shown by OmniCloud. OmniCloud polls for authorization, then discovers that user's assigned AWS accounts and permission sets, verifies the selected account with STS, encrypts the refreshable SSO token in MySQL, and requests short-lived role credentials only when performing an AWS operation. No AWS CLI, developer profile, static access key, customer role, or customer-side role setup is used.

Before deploying the backend, configure these production environment values:

1. `OMNICLOUD_PUBLIC_URL` is the canonical public HTTPS origin for OmniCloud. Keep the configured origin stable; it is checked against the browser origin for sign-in requests.
2. `AWS_SSO_START_URL` is the IAM Identity Center AWS access portal URL, `AWS_SSO_ISSUER_URL` is the IAM Identity Center issuer URL from its Settings page, and `AWS_SSO_REGION` is the region hosting that Identity Center instance. AWS's public OIDC client requires device authorization; its `RegisterClient` API does not support a hosted HTTPS redirect URI. See AWS [StartDeviceAuthorization](https://docs.aws.amazon.com/singlesignon/latest/OIDCAPIReference/API_StartDeviceAuthorization.html), [CreateToken](https://docs.aws.amazon.com/singlesignon/latest/OIDCAPIReference/API_CreateToken.html), and [RegisterClient](https://docs.aws.amazon.com/singlesignon/latest/OIDCAPIReference/API_RegisterClient.html).
3. `AWS_SSO_TOKEN_ENCRYPTION_KEY` is a randomly generated, base64-encoded 32-byte key. Keep it in a production secret manager, share the same key across backend replicas, and back it up securely. Changing it without a planned token re-encryption invalidates existing OmniCloud AWS sessions; users will need to reconnect.
4. Use a shared MySQL database for all replicas and configure production session cookies for the same HTTPS site. The schema bootstrap creates the per-user AWS SSO login/token tables. Clean expired `aws_sso_logins` rows on a schedule if the installation has heavy login traffic.
5. No AWS login credentials need to be installed on the OmniCloud host. Each user opens **Cloud connections**, clicks **Connect to AWS**, signs in and approves OmniCloud in AWS, and then chooses their assigned account and permission set. With a single assignment, OmniCloud connects it automatically.

IAM Identity Center's OIDC registration is created from the configured instance; registration secrets, device codes, access tokens, and refresh tokens are encrypted at rest with AES-256-GCM. Use a secure same-site OmniCloud login cookie and never log device codes or token payloads. Each connection is scoped to its owning OmniCloud user. Expired or revoked user sessions disconnect only that user's connection. Inventory, Terraform plan/apply/destroy, and monitoring request fresh short-lived AWS role credentials and verify account identity before use.

The initial connection verification uses STS `GetCallerIdentity` to confirm the selected account. Terraform needs the AWS service permissions for the selected template. The service pages provide private S3 buckets, `t3.micro` EC2 instances, Single-AZ encrypted MySQL RDS (`db.t3.micro`, 20 GiB), and DynamoDB tables provisioned at 5 read and 5 write units. These are low-cost/free-tier-oriented defaults, not a guarantee of zero charges; account age, eligibility, region, existing usage, and add-on usage affect billing. RDS uses AWS-managed master credentials in Secrets Manager, which may incur a separate charge; deletion skips a final snapshot and deletes database data. DynamoDB point-in-time recovery and secondary indexes are off by default.

AWS inventory and Monitoring require `ec2:DescribeInstances`, `ec2:DescribeSubnets`, `ec2:DescribeSecurityGroups`, `ec2:DescribeKeyPairs`, `s3:ListAllMyBuckets`, `rds:DescribeDBInstances`, `dynamodb:ListTables`, and `dynamodb:DescribeTable`; EC2 image/instance selectors also use `ec2:DescribeImages` and `ec2:DescribeInstanceTypes`. The RDS template also needs the relevant `rds:CreateDBInstance`, `rds:DeleteDBInstance`, `rds:CreateDBSubnetGroup`, `rds:DeleteDBSubnetGroup`, and describe actions. DynamoDB provisioning needs `dynamodb:CreateTable`, `dynamodb:DeleteTable`, `dynamodb:DescribeTable`, and tagging actions for OmniCloud resource tags. EC2 Terraform refresh needs `ec2:DescribeTags` in addition to the selector permissions. The chart’s monthly account actuals need `ce:GetCostAndUsage`; the optional 31-day account forecast needs `ce:GetCostForecast` and Cost Explorer enabled. Grant only the permissions needed for the services being tested. After an administrator updates the permission set, select **Connect to AWS** in Cloud connections to refresh the SSO session, then refresh the service page.

`AWS_LOCAL_PROFILE_MODE_ENABLED` is only a development compatibility switch. Production always disables that local-profile flow; the hosted OAuth flow above is the production AWS integration.

## Google Cloud onboarding

Set `OMNICLOUD_GCP_SERVICE_ACCOUNT_EMAIL` to the real service account used by OmniCloud's Google Cloud backend workload. Enable `iamcredentials.googleapis.com` in the OmniCloud service account's project as well as in customer projects. Do not create or distribute a service-account key. In production, the backend must use Application Default Credentials from workload identity as this configured service account. For local development, authenticate ADC as that same service account with `gcloud auth application-default login --impersonate-service-account="$OMNICLOUD_GCP_SERVICE_ACCOUNT_EMAIL"`; the developer identity must itself be allowed to impersonate it. The customer grants this OmniCloud service account `roles/iam.serviceAccountTokenCreator` only on the per-connection service account generated by the setup flow. See Google's [service account impersonation guidance](https://cloud.google.com/iam/docs/service-account-impersonation) and [generateAccessToken API](https://cloud.google.com/iam/docs/reference/credentials/rest/v1/projects.serviceAccounts/generateAccessToken).

The GCP setup flow is:

1. The signed-in user enters a Google Cloud project ID. OmniCloud creates a tenant-owned setup record and a unique customer service-account email for that connection.
2. OmniCloud displays Cloud Shell commands for the customer to enable IAM Credentials and Cloud Resource Manager APIs, create the service account, grant it `roles/browser` for project verification, and grant the configured OmniCloud service account `roles/iam.serviceAccountTokenCreator` on the customer service account. Compute Engine API and VM permissions are granted separately only if the user chooses the VM service in **Cloud services**.
3. The user runs those commands in the target project and chooses **Verify and connect**.
4. The backend uses Google Application Default Credentials and the Google Auth Library to mint a one-hour impersonated access token. It calls Cloud Resource Manager `projects.get` to confirm the service account can access the selected active project. The token is held only in memory for the request; only project ID and service-account email are stored.

Verification reports missing OmniCloud identity access, missing Token Creator binding, missing project read permission, missing APIs/service account, and inactive or unknown project separately. Setup, verification, and activation queries are scoped to the signed-in `user_id`. The Cloud services screen displays a separate, optional Compute Engine API and VM-permission command block. The account email is shown under the connected project in OmniCloud.

## Microsoft Azure onboarding and Terraform provisioning

Azure customer access uses Azure Lighthouse. Set `OMNICLOUD_AZURE_TENANT_ID` to OmniCloud's real managing Microsoft Entra tenant ID and `OMNICLOUD_AZURE_PRINCIPAL_ID` to the object ID of the OmniCloud service principal used by the backend. Never guess either identifier. This principal must match the backend identity that Terraform and API verification use.

Set `OMNICLOUD_AZURE_AUTH_MODE` to `cli` for local development, or `managed_identity`, `service_principal`, or `oidc` for a deployment host. Local CLI mode requires Azure CLI installed and authenticated to OmniCloud's managing tenant as the configured service principal. A backend-hosted managed identity is preferred in Azure. In service-principal mode, `ARM_CLIENT_ID`, `ARM_CLIENT_SECRET`, and `ARM_TENANT_ID` belong to OmniCloud's backend runtime only. In OIDC mode, inject `ARM_CLIENT_ID`, `ARM_TENANT_ID`, and a short-lived `ARM_OIDC_TOKEN` at runtime. Never put customer credentials in these settings. The backend obtains short-lived ARM tokens and does not store them.

The Azure setup flow asks the user for a customer subscription ID, customer tenant ID, and existing resource group. OmniCloud generates an ARM template that creates a read-only subscription delegation for discovery and disconnection, plus Virtual Machine Contributor and Network Contributor delegations limited to the selected resource group. A subscription owner (or an identity with the required role-assignment permissions) deploys the template at subscription scope. Compute and Network provider registration is shown separately on the Azure VM service screen because it is only needed if that service is used. OmniCloud verifies that the subscription is enabled, the tenant matches, and the selected resource group is readable before marking the connection connected. Microsoft's [Azure Lighthouse onboarding guide](https://learn.microsoft.com/en-us/azure/lighthouse/how-to/onboard-customer) describes the customer deployment requirements.

Disconnect is blocked while a managed VM or unfinished operation remains. OmniCloud then removes only the two Azure Lighthouse assignments generated for that connection. AWS disconnect removes the saved local-profile link only; it does not modify AWS permissions or sign out of the CLI. GCP disconnect removes its OmniCloud record; its customer-side service-account delegation must be revoked separately to remove cloud permissions.

The Azure Terraform service creates Ubuntu 22.04 Linux VMs in the connected existing resource group, along with a virtual network, subnet, NIC, and network security group. It uses an SSH public key only, has no public IP, and creates no inbound NSG rules. Supported sizes are `Standard_B1s`, `Standard_B2s`, and `Standard_B2ms`. Azure compute, disk, and networking charges may apply. The public key is stored with the deployment to support recovery plans; never submit a private key.

Requirements: Terraform CLI 1.5 or newer on the backend host and outbound HTTPS access to the Terraform provider registry on first initialization. OmniCloud provides an encrypted private S3 bucket template. GCP provides a Debian 12 Compute Engine VM template with an e2-micro, e2-small, or e2-medium machine type, a 10 GB standard boot disk, Shielded VM protections, and no external IP or ingress firewall rule. The app generates provider configuration and does not accept user-submitted HCL or arbitrary Terraform commands. Create and destroy require a reviewed plan and explicit confirmation; plans expire after 15 minutes. Each provider has isolated deployment tables and state folders under `backend/.terraform-state`.

Migration 005 is a historical AWS migration that disconnected previous AWS connections and removed the old CLI-profile column; the automatic schema initializer does not replay it. Migration 006 documents the GCP connection schema change, migration 007 documents GCP Terraform VM tables, and migration 008 documents Azure Lighthouse and VM tables. These schema updates do not delete customer resources or remove Terraform state. Provider deployment metadata, operation status, and plan summaries are stored in MySQL. Terraform plans, generated configurations, and state are separated by provider, user, connection, and deployment under `backend/.terraform-state`. Set `TERRAFORM_STATE_DIR` to a persistent, access-controlled, encrypted volume in deployment. The current Terraform executor is a single-host development implementation, not an isolated ephemeral-worker and remote-state design for production multi-tenant execution. Production needs isolated per-run workers and encrypted, locked remote state. `TERRAFORM_BIN` can point to Terraform when it is not on `PATH`.

Run `npm test` from `backend` to execute AWS, GCP, and Azure onboarding and verification tests. They use mocked cloud clients and do not require live cloud credentials or make live cloud calls. Run `npm run build` and `npm run lint` from `frontend/omnicloud` to check the UI.

## Local application deployments

The workspace Deployments page accepts a public HTTPS Git URL from GitHub, GitLab, or Bitbucket, clones it on the OmniCloud backend computer, uses its local Docker engine to build a linux/amd64 image, pushes the image to Amazon ECR, and creates an ECS Fargate service. The backend computer needs Git, Docker Desktop with its engine running, and outbound HTTPS access to the Git host and AWS. The repository must include a root Dockerfile configured to listen on the selected port. Private repositories and registry credentials are not supported. The flow streams local Docker, ECR push, and ECS deployment output to the browser using an authenticated event stream. It creates a private immutable ECR repository, ECS cluster, Fargate task definition and service, plus the task log group. OmniCloud discovers available subnets, security groups, and ECS-trusted role ARNs in the selected region. Select public subnets and a security group that permits inbound TCP on the app port; OmniCloud does not edit your network rules. The task receives a public IPv4 address and OmniCloud displays its current HTTP endpoint when the task starts. Task IPs can change after replacement; custom domains, TLS, persistent storage, and managed VPC/security-group creation are not included.

The connected AWS permission set needs iam:CreateRole, iam:PutRolePolicy, iam:TagRole, iam:GetRole, and iam:AttachRolePolicy for the task execution role controls; ecs:CreateCluster, ecs:DescribeServices, ecs:ListTasks, ecs:DescribeTasks, ecs:RegisterTaskDefinition, ecs:CreateService, ecs:DeleteService, ecs:DeregisterTaskDefinition, ecs:DeleteCluster, and ecs:TagResource; ecr:CreateRepository, ecr:GetAuthorizationToken, ecr:DeleteRepository, ecr:TagResource, ecr:BatchCheckLayerAvailability, ecr:InitiateLayerUpload, ecr:UploadLayerPart, ecr:CompleteLayerUpload, and ecr:PutImage; iam:ListRoles and iam:PassRole scoped to the selected execution role and conditioned on iam:PassedToService = ecs-tasks.amazonaws.com; iam:CreateServiceLinkedRole scoped to the ECS service-linked role ARN and conditioned on iam:AWSServiceName = ecs.amazonaws.com; and ec2:DescribeSubnets, ec2:DescribeRouteTables, ec2:DescribeSecurityGroups, and ec2:DescribeNetworkInterfaces. OmniCloud checks for AWSServiceRoleForECS and creates it before building the image when it is missing. The task execution role must trust ecs-tasks.amazonaws.com, have AmazonECSTaskExecutionRolePolicy for ECR pulls and log writes, and allow logs:CreateLogGroup so ECS can create its log group. Fargate, ECR image storage, public IPv4, logs, and network usage can incur charges. Delete the app in OmniCloud to stop its service and remove its cluster and image repository.

Google Cloud and Azure cards currently provide local browser-only demo records. They do not create cloud resources or contact those providers.

## Production settings

Set `NODE_ENV=production`, use a unique `SESSION_SECRET` of at least 32 characters, configure MySQL and Gmail, and serve the app over HTTPS. The session cookie is HTTP-only, SameSite=Lax, and marked Secure in production. Keep `.env` private.

For inventory and monitoring, the AWS IAM Identity Center permission set needs the read actions listed above (AWS list/describe actions commonly require `Resource: "*"`). Monthly actuals need `ce:GetCostAndUsage`; the optional account forecast needs `ce:GetCostForecast`; Cost Explorer must be enabled. After the administrator updates the permission set, choose **Integrate AWS** in Cloud connections to refresh the SSO session, then press **Refresh from AWS** in the service page. The connection check only validates STS identity and does not verify these service permissions.
Terraform provider packages now use a shared local plugin cache under the AWS state directory. Set `TERRAFORM_PLUGIN_CACHE_DIR` to another persistent directory if needed. Provider initialization still requires outbound HTTPS and adequate disk space; a full disk (`ENOSPC`) or blocked registry cannot be repaired by an AWS permission change.

The Deployments page can create a dedicated /omnicloud/OmniCloudEcsTaskExecutionRole role. This needs iam:CreateRole, iam:GetRole, iam:AttachRolePolicy, iam:PutRolePolicy, and iam:TagRole. OmniCloud attaches AmazonECSTaskExecutionRolePolicy and adds logs:CreateLogGroup scoped to /ecs/* log groups. The generated trust policy allows ECS tasks in this AWS account and includes SourceAccount and SourceArn protections.
